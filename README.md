# Dynamic CMS & API Builder - Go Backend Platform

This repository implements a production-grade Backend-as-a-Service (BaaS) platform (Dynamic CMS + API Builder) written entirely in Go.

It acts as a backend infrastructure generator allowing developers to dynamically create backend services, schemas, REST APIs, and GraphQL endpoints similar to platforms like Hasura or Supabase, but fully self-hosted and Go-native.

## System Architecture

The platform is designed around **Clean Architecture** and **Domain-Driven Design (DDD)** to ensure modularity, scalability, and maintainability.

### High-Level Architecture Flow

```text

   ┌────────────┴─────────────┐
   ▼                          ▼

                ▼

                │
                ▼

   ┌──────────────────────────┐

```

### Core Layers
1. **Presentation Layer**: Exposes HTTP REST endpoints using **Gin** and GraphQL queries/mutations using **gqlgen** (`internal/handlers`, `internal/graphql`).
2. **Application Layer**: Contains business logic (`internal/services`). Responsible for orchestrating operations, mapping rules, schema validations, and acting as intermediaries between the handlers and data store.
3. **Domain Layer**: Contains database entity definitions and structs (`internal/models/models.go`) which map perfectly to GORM objects.
4. **Infrastructure Layer**: Interacts with the underlying systems (`internal/database`, `internal/tracing`, `pkg/logger`, etc.). This layer handles metrics (Prometheus), structured logging (Zap), and telemetry (OpenTelemetry).

## Metadata Database Schema

The platform relies on a core internal metadata database (which defaults to SQLite for local development but supports external RDBMS). Key tables include:

- **`database_connections`**: Stores user-configured remote database credentials and connection pooling parameters (Host, Port, User, DB Name, Type).
- **`services`**: Represents dynamic data models (entities/tables). Each service maps to a remote database and specifies a physical `db_table_name`.
- **`fields`**: Represents the schema attributes (columns) mapped to a service. Field properties include `Type`, `IsNullable`, `IsUnique`, `DefaultValue`, and relation metadata (`RelationConfig`).
- **`roles` & `users` & `user_roles`**: Core Identity and RBAC system.
- **`service_permissions`**: Links roles to services, defining explicit CRUD control constraints and even row-level filters (`RowFilter`) and field-level permissions.
- **`migrations`**: Logs tracking automated DDL schema migrations generated by the system, tracking version history and rollbacks.
- **`backups`**: Records snapshot and table data state dumps for easy restorations.
- **`audit_logs`**: Logs tracking detailed data modifications across the platform.

## Core Components Implementation

### CRUD Engine & Query Engine
Managed by `DynamicDataService` (`internal/services/dynamic_data_service.go`), this component processes real-time HTTP requests mapped to dynamic schemas.
- Automatically interprets `GET`, `POST`, `PUT`, `DELETE` operations based on the provided service slug.
- The **Query Engine** parses URL parameters to dynamically compose filters (e.g. `?email=john@example.com`), pagination (`?page=1&limit=20`), and relation joins.
- Evaluates constraints and validates dynamic fields to prevent SQL injections or bad inputs.

### Schema Migration Engine
Managed by `MigrationService` (`internal/services/migration_service.go`), whenever a service schema is modified:
- Generates DDL queries internally mapped via GORM auto-migration mechanisms.
- Tracks operations (pending, applied, failed) natively in the `migrations` table.
- Contains references to schema snapshots for automated rollbacks.

### GraphQL Gateway
Managed in `internal/graphql/gateway.go`, leveraging `99designs/gqlgen`.
- Exposes `POST /api/v1/graphql`.
- Generates runtime schemas querying the metadata database (`services` and `fields`), allowing users to dynamically perform queries across their created entities.

### Backup System
Managed by `BackupService` (`internal/services/backup_service.go`).
- Enables table schema data snapshotting.
- Extracts JSON payloads of target schemas and dumps them into the metadata database for tracking.
- Supports generic restorations by ingesting snapshot payloads to rebuild rows.

### Observability Integration
The platform enforces high-visibility instrumentation:
- **Logging**: Zap structured JSON logger injected application-wide tracking correlation IDs (`pkg/logger`).
- **Metrics**: Prometheus middleware intercepting HTTP traffic measuring request durations, error rates, and hit counts (`internal/middleware/prometheus.go`). Exported at `/metrics`.
- **Tracing**: OpenTelemetry (OTEL) configured in `internal/tracing/tracing.go`, tracking deep dependencies and DB queries, exportable to Jaeger or similar systems.

## Unit Tests
The codebase aims for >80% coverage using the standard `testing` library. Tests are structured by domains (Unit, Integration, UAT) mapping against standard Go `httptest` tools and `sqlite` in-memory (`:memory:`) databases mimicking remote database connections dynamically.

- Ensure accurate coverage output by running tests over all packages.
- **Command:** `make test-coverage` (or `go test -v -race -coverprofile=coverage.out -coverpkg=./... ./tests/...`).

## Docker & Containerization
The repository is fully Dockerized for production readiness.
- `docker-compose.yml` launches the platform alongside internal monitoring tools (like Prometheus).
- Dockerized setup supports scaling backend instances seamlessly.
- **Run the stack:** `docker-compose up -d --build`.

## Swagger API Documentation
The API endpoints are fully documented using standard OpenAPI/Swagger conventions via `swag`.
- **Generation:** Generate using `swag init -g cmd/server/main.go --parseDependency --parseInternal --output docs` (Ensure `swag` CLI is installed).
- Once deployed, UI documentation acts as the source-of-truth for platform interaction endpoints (auth, models, builder, data).
