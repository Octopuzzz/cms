# CMS Backend Platform (Dynamic CMS + API Builder)

A production-grade Backend-as-a-Service (BaaS) platform written in Go, acting as a dynamic backend infrastructure generator.

## Core Technologies

*   **Language:** Go (latest stable)
*   **API Layer:** REST (default), GraphQL (optional using `gqlgen`)
*   **Web Framework:** Gin
*   **ORM:** GORM
*   **Logging:** Zap structured logging
*   **Metrics:** Prometheus
*   **Tracing:** OpenTelemetry
*   **Containerization:** Docker
*   **API Documentation:** Swagger / OpenAPI

## System Architecture Explanation

The CMS Backend follows **Clean Architecture** and **Domain-Driven Design (DDD)** principles, separating concerns into distinct layers:

*   **Presentation Layer (`internal/handlers/`, `internal/graphql/`)**: Handles incoming HTTP and GraphQL requests. It acts as the API gateway mapping requests to internal application services. The REST API is powered by Gin, and the GraphQL API is generated by gqlgen.
*   **Application Layer (`internal/services/`)**: Contains the core business logic. It includes the CMS Control Plane for service creation, the CRUD & Query Engines for dynamic data access, the Migration Engine, and the Backup Engine. Services interact with external dependencies through interfaces and the database connection manager.
*   **Domain Layer (`internal/models/`)**: Defines the core entities of the platform, including metadata representing `DatabaseConnection`, `Service`, `Field`, `User`, `Role`, and security primitives like `ServicePermission`.
*   **Infrastructure Layer (`internal/database/`, `internal/tracing/`, `pkg/logger/`)**: Provides cross-cutting concerns like dynamic database connection pooling for PostgreSQL, MySQL, and SQLite. It integrates robust observability mechanisms, including Zap for structured logging, OpenTelemetry for distributed tracing, and Prometheus for real-time metrics.

## Metadata Database Schema

The platform metadata is stored in a primary database (e.g., PostgreSQL). The key tables include:

*   **`database_connections`**: Stores credentials and connection properties for user-defined external databases.
    *   `id`, `name`, `type`, `host`, `port`, `username`, `password`, `database_name`
*   **`services`**: Represents dynamic data models created by users.
    *   `id`, `name`, `database_connection_id`, `db_table_name`, `created_at`, `updated_at`
*   **`fields`**: Defines attributes (columns) for a specific service.
    *   `id`, `service_id`, `name`, `type`, `nullable`, `unique`, `default_value`
*   **`service_permissions`**: Maps fine-grained access control rights (e.g., CanRead, CanCreate) between Roles and Services.
*   **`migrations`**: Audit log of all schema changes (add column, drop column) executed by the migration engine.
*   **`backups`**: Stores references to data snapshots and schema exports.
*   **`users` & `roles`**: Manages RBAC authentication and authorization for accessing the CMS Control Plane.

## CRUD Engine & Query Engine Implementation

The **Dynamic CRUD Engine** (`internal/services/dynamic_data_service.go`) provides instant RESTful endpoints for user-created services. When a `Service` is defined in the CMS, the CRUD Engine intercepts standard HTTP methods:
*   `POST /api/v1/data/{slug}` -> Dynamic Insert
*   `GET /api/v1/data/{slug}/{id}` -> Dynamic FindByID
*   `PUT /api/v1/data/{slug}/{id}` -> Dynamic Update
*   `DELETE /api/v1/data/{slug}/{id}` -> Dynamic Delete
*   `GET /api/v1/data/{slug}` -> Dynamic List

The **Query Engine** extends the `List` operation by providing advanced querying via URL parameters:
*   **Filtering**: `?field=value` maps directly to dynamic SQL `WHERE` clauses.
*   **Sorting**: `?sort=field:desc` maps to dynamic `ORDER BY`.
*   **Pagination**: `?page=1&pageSize=20` provides efficient `LIMIT` and `OFFSET` handling.

These operations are dynamically validated against the metadata schema, and role-based access control (RBAC) rules are applied before execution against the target database via GORM.

## Schema Migration Engine

The Schema Migration Engine (`internal/services/migration_service.go`) handles safe database schema evolution without downtime.
*   **Operations**: Supports adding, renaming, and dropping columns natively through GORM's `.Migrator()`.
*   **Safety**: Before altering tables, identifiers are validated against SQL injection regex rules. The engine executes diffs and logs the exact DDL commands and timestamps into the `migrations` metadata table. This acts as a foundation for historical tracking and future rollback mechanisms.

## GraphQL Gateway

The GraphQL Gateway (`internal/graphql/gateway.go`) optionally exposes data models via a dynamic GraphQL schema.
Powered by `gqlgen`, it provides a single unified endpoint `POST /api/v1/graphql` for clients needing complex nested data fetching. While the primary gateway interface is set up, it serves as a foundation for dynamically mapping AST nodes to internal `DynamicDataService` resolvers based on the CMS `Service` metadata.

## Backup System

The Backup Engine (`internal/services/backup_service.go`) protects data integrity by allowing users to snapshot dynamic services.
*   **Snapshotting**: Queries all rows for a target service and exports them into a JSON payload.
*   **Storage**: Backup metadata (timestamps, references, schema definitions) is saved into the `backups` table, providing endpoints for safe recovery or migration between environments.

## Observability Integration

Comprehensive observability is integrated globally to trace requests across dynamic infrastructure:
*   **Tracing (OpenTelemetry)**: Initialized in `internal/tracing/tracing.go`, requests are traced and exported to Jaeger. Spans cover HTTP handlers, database queries, and internal service execution.
*   **Metrics (Prometheus)**: `internal/middleware/prometheus.go` tracks real-time HTTP metrics including request latencies, status codes, and error rates. Metrics are exported at the `/metrics` endpoint.
*   **Logging (Zap)**: Structured JSON logging via `pkg/logger/logger.go` injects request context, trace IDs, and detailed contextual metadata for high-performance log aggregation.

## Unit Tests

The platform includes comprehensive test suites ensuring >80% coverage across Repository, Service, and API handler layers.
*   **Execution**: Run unit tests using `make test-unit` or full suite via `make test-coverage`.
*   **Strategy**: Unit tests leverage in-memory SQLite instances for high-speed, isolated execution without external dependencies. Handlers are validated using `httptest.NewRecorder` and `gin.CreateTestContext`.

## Docker Setup

The platform is designed for cloud-native deployment using Docker and Docker Compose.
*   **Dockerfile** (`docker/Dockerfile`): Uses multi-stage builds. The builder stage compiles the Go binary using `golang:1.23-alpine`, while the runtime stage uses a minimal `alpine:3.20` image for security and size reduction.
*   **Docker Compose** (`docker/docker-compose.yml`): Orchestrates the complete stack locally, spinning up the CMS Backend, PostgreSQL metadata database, Redis (caching/rate limiting), and a Prometheus server for metrics aggregation in a single `docker-compose up` command.

## Swagger Documentation

API Documentation is automatically generated from Go code annotations using `swag`.
*   **Generation**: Run `make swagger` to build the OpenAPI specs.
*   **Access**: Provides detailed, interactive schema documentation and security definitions for the CMS Control plane and dynamic engines.
